# Phase 2 — Frontend: Split-Pane Console

**Goal:** a single screen with a WhatsApp-style guest chat on the left and a live Admin Panel on
the right. Edit a rule on the right, send a message on the left, and the answer reflects the edit
immediately — no restart, no save button ceremony.

**Done when:** you can hand a laptop to a hostel owner and they can change check-in from 2 PM to
12 PM, ask "what time is check-in?", and see the new answer — without you touching anything.

**That demo is the entire point of Phase 2.** Every decision below is judged against whether it
makes that thirty seconds land.

**Out of scope:** auth, multi-property switching, persistence beyond the browser, streaming
responses, real WhatsApp. All roadmap R1+.

## 1. The three decisions that matter

### 1.1 Call the backend through a Next.js Route Handler, not from the browser

The browser talks to `/api/chat` on the Next origin; that Route Handler talks to Spring. The
Spring URL is a server-only env var and never ships to the client.

Why this over a direct `fetch` to `localhost:8080`:

- **The backend URL stops being public.** Today `/api/v1/chat` has no auth and costs money per
  call (review finding #9). A browser-side fetch publishes that endpoint to anyone who opens
  devtools. The BFF hides it.
- **CORS stops mattering.** Server-to-server; no preflight, no origin config to keep in sync.
- **It's where auth goes in R1.** When sessions arrive, the Route Handler attaches the token.
  No architectural change, just a header.
- **It's where rate limiting goes.** One place, before the paid call.

Cost: one extra hop in local dev. Worth it.

### 1.2 Route Handler, not a Server Action

Server Actions are for mutations that invalidate server-rendered data. A chat turn is neither —
it's a request/response with no cache to revalidate, and Phase 3+ will want token streaming,
which Route Handlers do natively and Server Actions do awkwardly. Use a `POST` Route Handler.

### 1.3 Zod at the boundary — one contract file

`lib/contracts.ts` holds zod schemas for `ChatRequest` / `ChatResponse` / `ProblemDetail`, with
TS types derived via `z.infer`. The Route Handler validates the outgoing request *and* parses the
backend's response before returning it.

Validating a response from a service you own feels redundant until the day the backend ships a
field rename and the UI renders `undefined` instead of erroring. Parse, don't assume.

> **Upgrade path, not now:** add `springdoc-openapi` to the backend and generate these types
> from the OpenAPI spec. Right, but premature while the contract is still moving. Hand-written
> zod is the correct call at this size — say so out loud in an interview, it's the kind of
> judgment they're probing for.

Two client components (`ChatPanel`, `AdminPanel`) with a shared parent holding the knowledge base
state. Everything else is presentational or server. Keep `'use client'` at the leaves it belongs
to, not on `page.tsx`.

## 3. State

`useConversation` is the whole state story:

```ts
type Status = 'idle' | 'sending' | 'error';

type UiMessage = {
  id: string;
  role: 'USER' | 'ASSISTANT';
  content: string;
  escalated?: boolean;
  meta?: { model: string; totalTokens: number; latencyMs: number };
  failed?: boolean;
};
```

Rules:

- `useState` + `useTransition`. **No Zustand, no Redux, no TanStack Query.** One list and one
  in-flight request does not need a state library, and reaching for one here reads as
  over-engineering rather than seniority.
- The hook is the seam: if Phase 3 needs streaming or optimistic retries, only this file changes.
- Append the user's message **immediately**, before the request resolves. A chat that waits 800ms
  to echo what you typed feels broken.
- On failure, keep the user's message in the list marked `failed` with a retry affordance. Never
  silently drop what someone typed.
- Send `history` as the messages *before* the current one, mapped to `{role, content}` — strip
  the UI-only fields. The backend caps length; don't duplicate that logic client-side.

`useKnowledgeBase` holds the KB string and mirrors it to `localStorage` (debounced ~300ms). A
demo where a stray refresh wipes the rules the owner just typed is a demo that dies in the room.

## 4. The Admin Panel

react-hook-form + `zodResolver`, one meaningful field (`knowledgeBase`) plus `propertyName` once
review item #7 lands.

- **Plain textarea, monospace, markdown or JSON — the owner's choice.** Do not build a structured
  form with "Check-in time" pickers. The whole product claim is *the owner writes rules in their
  own words and the AI understands them*. A structured form quietly contradicts that and boxes
  you into a fixed schema you'd have to break later.
- **No Save button.** Watch the field, debounce ~400ms, push into shared state. The next message
  picks it up. "Type here, ask there, it just knows" is the demo.
- Show a character count against the 20,000 cap, and mark the field invalid before the request
  goes out rather than surfacing a backend 400.
- `PresetPicker`: two or three seeded hostels (a Goa surf hostel, a Rishikesh retreat) so a beta
  tester has something to poke at in three seconds instead of typing a knowledge base from
  scratch. **Highest demo-value-per-line-of-code item in this phase.**

## 5. The chat UI

Mobile-width column (~390px) centered in the left pane, so it reads as a phone.

- Bubbles: guest right-aligned, concierge left-aligned. Timestamps.
- Typing indicator while `status === 'sending'`.
- Autoscroll to bottom on new messages — but only if the user is already near the bottom, so
  scrolling back through history doesn't yank them forward.
- `escalated === true` renders a distinct treatment: a muted "handing this to the manager" chip
  under the bubble. This is the field to make *visible* — it's what proves to a hostel owner that
  the AI knows what it doesn't know, which is the objection that actually blocks the sale.
- Per-message meta line (`gemini-2.5-flash · 470 tok · 823ms`) behind a small toggle. Owners
  don't care; you care during tuning, and interviewers notice that cost and latency were treated
  as first-class.
- Empty state with 3–4 suggested questions matched to the active preset. Clicking one sends it.

## 6. Error states

Map the backend's `ProblemDetail` to human copy — never render `detail` raw.

| Backend | UI |
| --- | --- |
| 400 validation | Inline field error on the Admin Panel or composer, before send where possible |
| 502 `model-unavailable` | Bubble: "The concierge is offline for a moment." + Retry |
| 500 / network / timeout | Same, with Retry |

The Route Handler should also enforce its own timeout (a little under the backend's) so a hung
upstream surfaces as a clean error rather than a browser spinner that never ends.

## 7. Styling & accessibility

Tailwind v4 is already wired with `@theme inline` in `globals.css`. Extend those tokens rather
than sprinkling hex values in components.

- Responsive: side-by-side at `lg:` and up; below that, stack into tabs (Chat / Rules). A hostel
  owner will absolutely try this on their phone.
- Dark mode already has a `prefers-color-scheme` block in `globals.css`. Honor it.
- The message list is a `role="log"` with `aria-live="polite"` so new replies are announced.
- Composer: `Enter` sends, `Shift+Enter` newlines. Disabled while sending, with the reason
  exposed to assistive tech — not just visually greyed.
- Every control keyboard-reachable with a visible focus ring. This is a portfolio piece; a11y
  gaps are the first thing a senior frontend interviewer looks for.

---

## 8. Testing

Keep it proportionate — this is a prototype UI, not a design system.

- **Vitest + React Testing Library** on `useConversation`: optimistic append, failure marks the
  message `failed` and preserves it, history mapping strips UI-only fields.
- **One Route Handler test**: invalid body → 400 without calling upstream; upstream 502 → mapped
  error shape.
- **Skip component snapshot tests.** They'd break on every styling tweak and prove nothing.
- Manual pass against the Phase 3 question list ("Can I bring my dog?", "How much for a dorm
  bed?", "Can a car come to your gate?") before showing anyone.

## 9. Definition of Done

```bash
cd frontend && npm run build
```

```bash
cd frontend && npm run lint
```

Then, with the backend running:

- [ ] Editing check-in time in the Admin Panel changes the next answer — no reload, no restart
- [ ] An out-of-scope question renders the escalation treatment
- [ ] Backend stopped → chat shows "concierge is offline" + working Retry, no unhandled rejection
- [ ] Page refresh preserves the knowledge base (conversation resetting is fine and expected)
- [ ] `NEXT_PUBLIC_` does not appear anywhere near the backend URL; devtools Network shows only
      same-origin `/api/chat`
- [ ] Usable at 390px wide and keyboard-only
- [ ] `npm run build` clean, no type errors, no `any` in `lib/contracts.ts`
